## 5.2 Public events

The site shall allow visitors to:

- View upcoming events.
- View past events.
- Open an event detail page.
- See date/time, location, and description.
- See sponsors or partners when marked for publication.
- Register when registration is enabled.

Events are presented as a list in the initial release. A calendar view is a possible future enhancement, pending research into a suitable approach; the data model should not preclude it.

**Implemented:** `/events` lists upcoming and past events read live from Supabase (`public_events`) and opens event details in a sheet (with `/events/e/[id]` kept as a direct-link detail page, and `/events/[id]` permanently redirecting there for links shared before the move) showing date/time, location, description, and public sponsors/partners (`public_event_sponsors`, sourced from `event_sponsors`/`people` and limited to sponsors marked `is_public`), plus a public registration form (when `registration_enabled` and within the registration window) backed by `event_registrations` and the `register_for_event()` RPC (see [§6](../technical-spec.md#6-proposed-data-model)). After the response, the registrant receives their own confirmation (#1068, kind `event_registration_confirmation`, which is deliberately not in `NOTIFICATION_KINDS`: they hold no portal account and so no preference row, and only the tenant's org-wide email switch governs it). It restates the event, its window in the event's own timezone with the zone labelled, its place and the party size, links to the public event page on the tenant's own domain, and attaches the event as a `text/calendar` file; it deliberately echoes back neither the phone number nor the notes. Staff are not notified of a new registration -- tracked separately.

**The form waits to be asked for** (#1256). Registration is offered as a single **Register** button, and the fields appear only when it is pressed -- on a phone the sheet's first screen was a form, so the reader was asked to fill something in before the flier, the date line and the description had told them what it was. The button is a disclosure, not a route: the sheet's own URL is worth sharing, "I have started filling in a form" is not, and pushing history for it would put Back between the reader and the listing. It carries `aria-expanded`/`aria-controls`, moves focus to the first field on reveal, and keeps what has been typed if it is collapsed again; the submit is `Complete registration`, deliberately not a second `Register`. Status is _not_ behind it -- somebody already registered, or past the deadline, is told so with no button to press, because that sentence is the answer the button would otherwise raise.

**A signed-in visitor is not asked to retype what the account already holds** (#1257). `loadEventViewer()` distinguishes a session with no approved claim ([§5.23](constituent-accounts.md#523-constituent-accounts)) from a visitor with no session at all: the first still registers down the anonymous path, but its name and email arrive prefilled from `auth.users` -- the verified address, and a display name from the OAuth metadata where the provider gave one -- above a single `Signed in as …` line. Both fields stay editable, and the submission still goes through `register_for_event()`, which matches or mints the `people` row as before; the point is that a retyped address is how a duplicate gets made. Everything on that screen is derivable from the caller's own session and nothing from the directory: a form that changed according to whether the address matched a `people` row would answer "do you have a record of this person?" for anybody who can make an account, which is what [§5.23](constituent-accounts.md#523-constituent-accounts)'s silence rule refuses.

An event must support these fields:

- Name
- Description
- Start and end date/time, including timezone
- Location or location description
- Status: draft, published, cancelled, or archived. Whether an event is over is derived from its dates (Upcoming / Today / Past), not stored: `completed` was removed in #1609, since it had to be set by hand and took the event off the public site
- Public/private visibility
- Registration enabled/disabled
- Optional capacity
- Optional public registration deadline

Future event capabilities may include registration status, waitlists, and event photos.

## 5.5 Event management

Authorized users shall be able to create and manage events, including:

- Name
- Location
- Date and time, including timezone
- Sponsors
- Associated expenses
- Giveaway sales
- Public/private visibility and publication status

The event record should support a public/private boundary so internal planning details do not become public accidentally. Registration, volunteers, and inventory distributions may be added as later capabilities. Attendance is implemented as a simple event-level headcount (`attendance_count`, `attendance_notes`) rather than per-attendee records — a deliberate product decision, not a placeholder.

**Also implemented, on `events` itself:** an event lead (`event_lead_id` → `auth.users`), capacity, and an after-phase report workflow (`report_status`: not_started/in_progress/submitted, `feedback_notes`, `content_notes`, `report_submitted_at`, and since #1579 `report_snapshot`, the figures frozen on submit — see "Submitting freezes the figures" below), surfaced on the event editor's Report card. **The Report card's summary is computed, not typed** (issue #1576): read-only Money, Goods, Sponsors, Team, Guests and Operations sections come from `get_event_report_data(event_id)`, a security-definer RPC returning raw rows per section that the definitions in `src/lib/portal/event-report-metrics.ts` total. Each section is null — and not rendered — for a caller without its permission (Money: `finance_reports: view`; Goods: `finance: view`, `finance_reports: view`, `inventory: manage` or `inventory_reports: view`; Sponsors, Team and Operations: `events: view`), so a tenant without Finance has no Money section, and a visible section with nothing recorded says so instead of showing zeros. Guests reuses the Impact card's figures (`get_event_impact_derived_data`), so no participant figure is defined twice. Money reuses the Finance definitions (`summarizeByEvent`): **net is income less paid spend**, exactly as Finance → Reports counts it, with approved-but-unpaid spend shown beside it as _Committed_. Income includes giveaway ticket sales, which the Finance rollup (`get_finance_report_data`) now reads too, so the two pages agree. A sponsorship's mirrored cash (`monetary_donation_id`) or in-kind items (`donation_id`) are counted once, under sponsorship, never again as donations. Event-linked cash donations (`monetary_donations.event_id`) have their own read-only **Cash donations** card in the rail's Money group (issue #1577), behind `finance: view` like Finance → Donations, which it links to filtered to the event; a sponsorship's cash mirror is listed there and marked. The **Impact** card gains _people served_ — items distributed, distinct recipients and value given out — from the event's `distributed` inventory movements, through the same definition the Report's Goods section and the Program Impact Report use. **Each list card summarizes itself** (issue #1586): Volunteers, Sponsors, Donations, Cash donations, Distributions and Expenses open on a row of figures above their list — volunteers, shift slots filled, hours logged and volunteers not on a shift; sponsors by support type, stated contribution and follow-ups outstanding; in-kind items received, distinct donors and face value, with sponsor items shown apart as counted under Sponsors; cash donations and, apart, cash sponsorships; quantity distributed, distinct recipients and value given out; and expenses paid, approved and awaiting approval, with budget remaining after paid and approved expenses (the Report's budget remaining also subtracts reimbursements, which the Expenses card does not list). Each is computed from every row the card loads, not its preview, through the same `event-report-metrics.ts` definitions as the Report, and a card with no rows shows its empty state rather than zeros. The typed `report_summary` column is retired: nothing writes it, and text written before #1576 is shown read-only as "Earlier written summary". **The Report card's retro is structured** (issue #1578): `lessons_learned`, one author's free text, is replaced by `event_retro_items` — _went well_, _to improve_ and _action_ items, each with its own author and an optional area naming the Report section it is about (money, goods, sponsors, team, guests, operations). Action items carry an optional owner from the event's staff roster and an open/done status. Anyone on the event's staff roster (`event_staff`, matched to the signed-in account through `people.auth_user_id`) who holds `events: view` adds items, and edits and removes their own; `events: manage` adds to any event's retro and changes any item — enforced by `can_write_event_retro(event_id)` in RLS and again in the Server Actions. Volunteers are on `event_volunteers`, not the roster, so they cannot. A submitted report freezes the retro except for marking an action item done or open. **Open action items carry forward**: the Checklist card of every later event that shares a program with the item's event (see [programs](programs.md)) lists them until someone closes them; an event in no program carries nothing forward. The event page's rail shows _Retro not started_ on the Report card for a started event with no items, and _N open action items_ while any of its own are open. Existing `lessons_learned` text was archived as one `improve` item per event (with no author, shown as "from the earlier written report"); the column is kept because `seed_demo_tenant` still writes it, and a trigger turns anything written there into an item. `location` is the single place field: a `venue` column described the same thing a second time — the public pages already rendered `venue ?? location` — and was merged into it. There is no event-type field either: the programs an event counts toward _are_ its categorisation, so `event_type` and its curated `src/lib/event-types.ts` list were both removed. **An event can belong to any number of programs**, through the `event_programs` join table rather than a single `program_id` — one access day can serve two programs, and the Program Impact Report counts it in full for each, since both genuinely ran it.

**Report and Impact are one Results card** (issue #1588). The two cards had grown to show the same figures twice, and Impact could change under a submitted report. The **Results** card shows, in order: **Outcomes** — participation (participants, checked in, first-time and recurring participants, and with the rider-profile module beginners and _first time on snow_), people served (items distributed, recipients, value given out), assistance given (rental subsidies and participant assistance) and assigned discount codes with the discount value they offered (#1589, never part of assistance) — computed by `src/lib/portal/impact-metrics.ts` over `get_event_impact_derived_data`; then the Money, Goods, Sponsors, Team and Operations sections above, from `event-report-metrics.ts` over `get_event_report_data`, with distributions moved out of Goods into Outcomes; then the free text — participant feedback, photos/content, impact notes (`event_impact_notes.notes`) and the retro. No figure appears twice. **Report figures are never typed**: a number is derived from records captured where the work happens, and the only things written at report time are text. The four figures `event_impact_notes` still held as typed numbers are derived or dropped: _first time on snow_ counts checked-in attendees whose rider level (snapshotted at check-in) is the new `first_time` level, below beginner; _rental subsidies_ count rental-kind discount codes held by a registrant who did not cancel; _participant assistance_ is the value of assigned codes plus the value given out in distributions plus paid `event_expenses` flagged `participant_assistance`, each part shown so the total can be traced; and _beginners paired with experienced riders_ is dropped, since nothing records a pairing. On an event that auto-assigns a code to every registrant, codes count toward neither subsidy nor assistance. The four typed columns are archived, not dropped: nothing writes them, and an event that holds a value shows it read-only as "Entered by hand (archived)", never added to a derived figure. Status, Submit and Reopen apply to the whole card, and submitting locks all of it, including the impact notes (refused server-side until reopened). The card is in the rail for `events: view` or `event_impact: view`, and each section stays gated by its own permission or module; the route itself still requires `events: view`. `?tab=report` and `?tab=impact` links land on Results, and the rail's separate "Impact not recorded" task is gone — with nothing to type, "recorded" can only mean the report.

**Submitting freezes the figures** (issue #1579). Live figures keep moving after an event — a late expense is paid, a sale is voided — and a grant report built from a submitted report must not move with them. `submit_event_report(id)` (`events: manage`) sets the status and, in the same statement, stores the report's raw rows — `get_event_report_data`'s Money, Goods, Sponsors, Team and Operations sections — in `events.report_snapshot` with a `captured_at`. It is written in the database rather than by the submitter's session so that it is complete: a coordinator with `events: manage` and no `finance_reports: view` still freezes Money. Rows are frozen rather than totals so `event-report-metrics.ts` stays the one definition, applied to frozen and live rows alike. `get_event_report_data` returns the snapshot under a `snapshot` key, each section gated by the same permission as its live one, so the board still reads frozen Money and nothing else. A submitted report renders the frozen figures, and each one that has changed since carries its current value ("Changed since submission: $1,180.00 now"); the comparison (`eventReportDrift`) is to the cent and only across sections the reader sees on both sides. `reopen_event_report` clears the snapshot. A trigger refuses any other write to the column, since the events update policy would otherwise let any `events: manage` caller set one. Outcomes are not frozen. Reports submitted before #1579 have no snapshot and keep showing live figures: they were not backfilled, since today's figures labelled "at submission" would be wrong.

**Also implemented, as separate per-event tables/tabs on the event editor:** planning-phase logistics (`event_logistics` — meeting point, gear requirements, transportation, food, supplies, emergency contact, notes; one row per event) and a during-phase incident log (`event_incidents` — description, severity: minor/moderate/serious, people involved, occurred-at, reporting user; restricted to `admin`/`event_coordinator` since incident detail is more sensitive than the rest of the events cluster). This event-scoped incident log satisfies the operational need described in [§16.1](addenda.md#161-incident--problem-documentation), though it is narrower than that addendum's proposed cross-cutting `incident_reports` table (no inventory-item linkage, no open/resolved workflow) — see [§16.1](addenda.md#161-incident--problem-documentation) for the remaining gap.

### Registering as yourself

**Implemented** (issue #1165, epic #1160). A visitor with an account that is linked to a directory record gets a different registration form on a public event page: prefilled, and attached to the `people` row they already have. `register_myself_for_event()` takes no name and no email, so unlike the anonymous `register_for_event()` it never calls `resolve_or_create_person_by_email()` — which removes the largest single source of duplicate `people` rows. Everything else is deliberately identical, because it is a property of the event rather than of who is asking: the same `(route, ip)` rate limit, the same public/published/`registration_enabled`/deadline checks, the same `for update` lock on the event row before seats are counted (so the two registration paths queue behind each other rather than each overrunning a capacity the other has filled), and the same discount-code assignment. `event_registrations_event_person_key` is what makes a second attempt `ALREADY_REGISTERED`.

**The participant agreement is kept on file** (issue #1401). Where the tenant has a waiver in force, the first acceptance on this path is written to `person_waiver_acceptances` (tenant, person, version, `accepted_at`) as well as to the registration. On the next event, `my_waiver_on_file()` returns that acceptance while its version is still the one in force, and the form replaces the agreement and its box with one line — "Participant agreement v3 · accepted Oct 4, 2026 · view", linking `/waiver?version=3`. The RPC then accepts an unticked submission and copies the on-file version and `accepted_at` onto the new registration, so `waiver_version`/`waiver_accepted_at` mean what they always did. Publishing a new version makes the file stale at once and the full block returns; a submission made against a summary the republish overtook is refused as `WAIVER_CHANGED`, not `WAIVER_REQUIRED`, since there was no box to tick. **Linked accounts only:** `register_for_event()` never writes the file, because its person is an email match and an email match is not identity. No expiry yet — a per-tenant period (per season, as Smartwaiver and WaiverForever offer) would be a filter on `accepted_at` in `waiver_on_file()`.

Party size, phone, pronouns, Instagram handle and a note may be corrected on the form; they land on the registration and are **not** written back to `people` (see [§5.9](people.md#acting-from-your-account)). Somebody already registered is shown that, rather than a second form. There is no cancel: `event_registrations` has no cancelled state and no delete path anywhere in the application, so the only thing a button could do is destroy the row, and with it the attendance figure and any assigned code.

### Instagram handle or preferred contact

**Implemented** (issue #1647, epic #1646). A per-tenant setting, **Require an Instagram handle** (`registration.requires_instagram` in `app_settings`, in the **Registration** sheet on the portal Events page, `events: manage`), for an organization that plans an event where its registrants are — Chatter Snow coordinates carpools on Instagram. **No row means off**, so no other tenant's form changes; the migration turns it on for Chatter Snow.

**On**, both registration forms make the Instagram handle required and offer **"I don't have Instagram"** beneath it. Ticking it hides the handle and asks for a **preferred contact method** (Text message, Phone call, Email, WhatsApp or Other — not editable by staff in v1) and the **contact detail**; for Email the detail may be left blank to mean the address they registered with. The review step and the confirmation email show the same answer under "How we'll reach you". **Off**, the forms are unchanged and the registration RPCs store whatever handle arrived exactly as before and null in the new columns, whatever was sent.

`resolve_registration_contact()` is the one validator, used by both registration RPCs (which read the setting themselves and refuse with `INSTAGRAM_OR_CONTACT_REQUIRED`), by the registrant's own change (`set_my_registration_contact()` on `/my/registration/[id]`, `submit_registration_contact_by_token()` on the answers link) and by staff (`set_registration_contact()`, never required). The public API takes `has_no_instagram`, `preferred_contact_method` and `preferred_contact_detail` and is held to the same rule on a tenant with the setting on.

**Registrants change it themselves** from a "How we reach you" card on the answers link and on `/my`. The link page prefills the handle — a public handle, the reasoning the CSV export uses — but **never a phone number or address**: it shows "Contact on file: Text message" and asks for the detail again to change it, so a forwarded link keeps #1502's rule that the page shows no contact details. Because the link is how a registrant without an account changes it, **the answers link is now issued whenever there is something on it to change** — current questions, or this setting on (#1649's carpools will join the condition) — and the page shows only the cards that apply.

**Staff** see and edit it in the registrant detail sheet; the add-registrant and walk-in dialogs keep it optional. The registrants list's Instagram column shows the handle, or "No IG · Text" with the detail in a tooltip for `events: manage`. The answers CSV carries the preferred contact method on every row and the detail only on rows whose `shares_contact` consent was ticked, like email and phone.

### Have you been before?

**Implemented** (issue #1259). Both registration forms ask one more question — "Have you been to one of our events before?" — and store the answer on the registration as `event_registrations.attended_before`. An organizer knows who to look after on the day, and a claim reviewer ([§5.23](constituent-accounts.md)) gets the one piece of evidence that helps most when an email matches nobody: "I came to the November swap" is a record to go and look for.

Three things make it work, and each one is a rule rather than an implementation detail.

**It is asked of everyone, identically.** A question that appeared only for addresses matching no `people` row would tell the reader whether the organization has a record of them, which is precisely the enumeration answer the claim flow refuses to give. The cost of asking somebody we already know is one redundant question; the cost of asking selectively is an oracle. `register_for_event()` branches on nothing about the address, and the field renders the same for a visitor with no session, an account whose claim is unapproved, and a linked constituent. It is a field on the form rather than a step after the write, because a step after the write is one that can be abandoned.

**Unanswered is a third state.** The column is nullable, null means the question was not answered, and nothing anywhere may read that as "no". Every row that predates this ticket is null, so a count that folded them into the first-timers would be wrong by the whole population. `countSelfReportedFirstTimers()` counts `=== false`, and the portal shows the column only once somebody has answered.

**It never replaces the derived figure.** First-time versus returning is computed from check-ins — `computeFirstTimeParticipants()`, `get_event_impact_derived_data`, the People segment counts — and those are unchanged and remain the only source for anything that reaches an impact report. A self-reported answer and an attendance record are different facts, and the portal shows them side by side with the wording carrying the difference ("1 first-time" against "1 said it would be their first"). The register-as-yourself form asks it too rather than deriving it from `my_event_history()`: the ledger only knows the events this tenant ran on this platform, and seeding the one self-reported column from the derived one would make it a second copy of the thing it exists to sit beside.

It appears in the portal on the event's registrant list (a column and a count) and on the person record's Event registrations card, worded as a quotation. It appears nowhere public.

### Is anyone in the party under 18?

**Implemented** (issue #685). Both registration forms ask one more question — "Is anyone in your party under 18?" — and a yes collects the accompanying adult's name and mobile number and an emergency contact. `/code-of-conduct` and `/terms` have said since they were written that a minor takes part only with a parent or guardian; nothing in the product knew whether one was coming, so a party of four could be one adult and three children and the first anyone found out was on the day.

**The platform ships the mechanism and none of the rule.** What an organization _requires_ — who must accompany, whether that adult registers too and counts in the party size, whether there is a minimum age at all — is that organization's claim, so it is the `events.minor_accompaniment` content slot, blank until somebody writes it, exactly like `get_involved.volunteer_screening` ([§5.11](volunteers.md)). A tenant that has adopted nothing shows nothing, promises nothing, and still gets the flag on its registrant list. What the form _asks for_, and that it never asks a date of birth or an age, is a fact about this software and renders on every tenant from the component. That split is `docs/legal-basis.md` rule 2, and `minors.test.ts` checks the second half against the schema.

**Required on the forms, three-state in the column.** Unlike "have you been before?", which has a real "rather not say", this question is required: the accompanying-adult block, the organizer's flag and the organization's own rule all hang off the answer, and an unanswered one leaves the gap the field exists to close. `event_registrations.party_includes_minor` stays nullable all the same, and null means **nobody was asked** — every row written before this shipped, every walk-in and staff-added registrant, and every caller of the public API, whose published contract predates the question. Nothing may read null as "no". The RPCs enforce only the conditional: a `true` that arrives without all four contacts raises `MINOR_CONTACTS_REQUIRED`.

**Asking is a per-tenant setting** (issue #1416). The question is asked unless an organization turns it off from the **Registration** button on the portal's Events page (`events: manage`). The setting is `registration.asks_about_minors` in `app_settings`, and a missing row means on, so every tenant, new tenants included, asks unless it decides not to. Chatter Snow has it off. With it off, neither form renders the question or the contacts, and both registration RPCs ignore an answer or contacts that arrive anyway (the public API included) and store null, the column's "nobody was asked". Nothing is dropped: the columns, `events.minor_accompaniment`, `MINOR_CONTACTS_REQUIRED` and the retention rule stay, and contacts stored before the setting was turned off are still cleared on the usual schedule. The public form reads the setting through `public_registration_settings`.

**A per-event note in the confirmation email.** `events.confirmation_note` (plain text, up to 1000 characters, null by default) is a "Confirmation email note" field on the event's Planning tab. When set, the registration confirmation adds it as its own paragraph under the event details and answers, above the event link, in both the HTML and text parts; blank renders nothing, so an event without one gets the same email as before. It is for what everyone registering for that one event needs, such as what to bring, and is separate from the tenant-wide wording in Automatic replies. It is not in `public_events`, so it reaches registrants only.

**Adults only (18+) is a per-event setting** (issue #1417). `events.adults_only`, off by default, is a switch on the event's Planning tab. On, the public site shows an **18+** badge on the event card, the detail page and the sheet header; step 2 of registration asks a required, unticked "Everyone in my party is 18 or over" instead of the under-18 question, which an 18+ event never asks whatever the tenant setting says; and both registration RPCs refuse a registration without `p_adults_only_confirmed = true` (`ADULTS_ONLY_CONFIRMATION_REQUIRED`, shown on step 2), discard any under-18 answer, and record the confirmation as `event_registrations.adults_only_confirmed_at`, shown in registrant detail. Off, the confirmation is ignored and nothing about age is asked beyond the tenant setting. The public API exposes `adults_only` on events and takes `adults_only_confirmed` on a registration.

**Nothing is accepted here.** Per [§5.22](../technical-spec.md), these paragraphs are notice: no checkbox, no stored pointer to a version. The one box on the registration form carrying a real choice is the participant agreement's, and a second box nobody can decline would dilute it. The single thing a registration submission now carries is the photo agreement below (#1376), which is a claim the organization makes in its own words and is deliberately not called consent — it does not reach this question, and nothing about a party including a minor is agreed to by submitting.

**The flag and the contacts are gated differently, and the contacts are gated by privilege.** Any holder of `events: view` sees that a party includes someone under 18 — the door shift has to know before the day, not at it. The four contacts are readable only at `events: manage`, and not by convention: 20260922040000 revokes those columns from `authenticated` on `event_registrations` and serves them through `event_registration_minor_contacts`, a security-definer view carrying its own tenant isolation and its own permission check. The rider block beside it is gated in TypeScript alone, which was an acceptable cost for a riding preference and is not one for a guardian's mobile number. The four are cleared by the retention purge with the other personal fields; the flag survives beside `party_size`.

It appears nowhere public, and deliberately not on the person record: the answer describes one party at one event, and a standing "brought a minor" marker on somebody's directory row is a different and more sensitive claim than the one that was collected.

### Photos and video

**Implemented** (issues #599, #1376). #599 asked a question at registration — the organization's own paragraphs above an unticked box — and #1376 reversed it. **Registering for an event is itself the agreement to being photographed, and the remedy is removal**: any photo can be taken down on request, at any time. There is no box, and a decline box as an opt-out was declined too. The decision is recorded in [`docs/legal-basis.md`](../legal-basis.md), "Registering carries the photo agreement", which partially supersedes #1318 for this one form.

**The word "consent" is gone from every surface a human reads, and the column names stay.** Agreement implied by submitting a form is not an unambiguous affirmative act, so calling it consent in a privacy policy would misstate the lawful basis; the honest framing is notice plus a standing right to object. Renaming `photo_consent` to `photo_objection` would mean retyping both registration RPCs, the column grant list, a published API field, the generated types and every test, for a name — so `20260923020000` is a comments-only migration that flips what the columns mean and touches no row.

**The mechanism is the platform's and the implication is the organization's, and here blank removes the notice rather than softening it.** `events.photo_consent` is empty on every tenant by default, and empty means no heading, no notice, no paragraphs and a registration form byte-identical to the one before #599 — which is where almost every tenant stays. That is [`docs/legal-basis.md`](../legal-basis.md) rule 2 at its sharpest and #1376 sharpened it again: what an organization does with a photo of somebody's face is off-platform, and since these paragraphs are what makes registering carry the agreement, a default here would be the platform implying an agreement on a tenant's behalf. The platform adds no sentence of its own beneath them: how to object is the organization's to say in its paragraphs.

**Three states, and only one has an operational job.** `null` means **no objection on record** — agreement implied by registering — and is the resting state of every registration this platform takes, along with every row that predates #599, every walk-in, every staff-added registrant and every API caller that did not ask. `false` means **objected: do not photograph**, and it is what somebody checks before pointing a camera. `true` means the objection was withdrawn, or that an API caller that genuinely asked recorded an explicit confirmation. Nothing may read `null` as an objection, and **nothing writes `true` at registration** — a form with no affirmative control cannot produce an affirmative record. **No row was backfilled and none needed to be**: `false` means exactly what it meant under #599, and `null` meant "nothing to act on" under both models.

**A snapshot rather than a version pointer**, which is #1319's test rather than #686's: the version-table shape earns its cost only where the text must be citable from outside the row that holds it, and a content slot has no version table and no permalink. `resolved_photo_consent()` reads the paragraphs from `site_content` itself and joins them, so the words are never supplied by whoever posts the form — the invariant `artwork_submissions.consented_terms` carries. Since #1376 `photo_consent_text` is a copy of what somebody was **told** when they objected rather than of a question they were asked, and nothing writes it at registration time.

**Not a fifth legal document.** #686 made the waiver one because a release of legal rights is one: sections, a version history, an address somebody can be sent to. This is a notice and a record, so there is no `/photo-consent` route, no registry entry, no `legal_publication.*` row and no `legal_surface.*` key — the last because a surface key meaning "this tenant publishes a photo notice" would tell every tenant with its own published documents that it had drifted.

**No guardian branch.** #599 reworded the box where the party included someone under 18, so the registering adult answered in a parent-or-guardian capacity. With no box there is nothing to reword, and a platform-written sentence saying an adult's submission binds the under-18s in their party would be a guardianship claim the platform is in no position to make. A tenant's own paragraphs cover minors if it wants them covered.

**Objecting: three routes, one of them self-service.** Telling any organizer at the event, emailing, or — only for somebody who has claimed an account (see [§5.23](constituent-accounts.md)) — `set_my_photo_consent()` from `/my/registration/[id]`. That last resolves through `my_constituent_person_id('events')` and most registrants have never claimed an account, which is why the privacy policy names the organizer and the email first and qualifies the third rather than promising it. `my_photo_consent()`'s `asked` flag is computed from the tenant's slot alone, with no reference to the row's own columns, so the control appears for every registrant of a tenant that publishes a notice — including the overwhelming majority whose three columns are null. The RPC refuses a `null` write with `PHOTO_CONSENT_REQUIRED`, because letting somebody write `null` back would erase the record of having objected, and refuses with `PHOTO_CONSENT_UNAVAILABLE` where the organization publishes no notice, rather than silently clearing a row an organizer acts on.

**Staff see it where it is needed, at `events: view`.** A `No photos` badge beside the name on the event's registrant list, rendering only for an objection, and all three states in the registrant sheet with the snapshot behind a disclosure. The Happening Now check-in sheet renders the same list, so the badge is at the door with no second copy. **That badge is why #1376 kept the columns at all**: dropping them would have deleted the list the door shift checks, and "photos can be deleted" is a remedy after the fact rather than a list of people who asked not to be photographed.

**Retention clears all three, which is the opposite call from the waiver's on the same row** — see `docs/legal-basis.md`, where the rationale is restated against the new meanings: an instruction about a face nobody can identify is no more useful than a permission was.

### Event media (photos and video taken at the event)

**Implemented** (issues #1606, #1607 and #1608, part of #1605). Photos and videos taken at an event are uploaded from the event's **Media** card (the rail's Results group) into the private `event-media` bucket, at `{tenant_id}/{event_id}/{uuid}.{ext}`. **Photos** (JPEG, PNG, WebP, and HEIC/HEIF converted in the browser) are re-encoded with `compressImage` to 2048px on the longest edge — JPEG, or WebP where the original may carry transparency — and uploaded in one request to a signed upload URL; a HEIC the browser cannot decode is refused with a message rather than stored undisplayable. **Videos** (MP4, MOV, WebM, up to 10 GiB) go up by resumable (TUS) upload: a Server Action mints a signed upload token with the uploader's own session, and the browser sends it as `x-signature` to `/storage/v1/upload/resumable/sign` in 6 MB chunks (`tus-js-client`). Each file shows its progress; a video can be paused, and a dropped or failed one resumes from the last acknowledged chunk. Several files, photos and videos mixed, upload two at a time.

**Who:** reading is `events: view`; uploading is `events: manage`, or `events: view` and on the event's staff roster — `can_upload_event_media(event_id)`, which also requires the event to be the caller's tenant's, the tenant's setting on, and not the demo tenant. The bucket enforces its own `allowed_mime_types` and `file_size_limit`, so a PDF or an oversized file is refused by storage, not only by the client. **The hosted project's global upload limit (Dashboard → Storage → Settings) must be at least the bucket's**, or it caps uploads first; `supabase/config.toml` sets the local one to match.

**Viewing** (#1607): the card shows photos as a thumbnail grid — the stored, already re-encoded photo is the thumbnail — opening a lightbox with next/previous, zoom and download, and videos as a list (filename, size, uploader, upload time in the viewer's zone, labelled) with play in a dialog and download. Every URL is a signed URL minted on each load with the reader's own session, valid for an hour and never stored; a download is the same signature with `download=<original filename>`. Photos can be ticked (or all) and downloaded as one .zip, assembled in the browser so no server holds the files. **Delete** is `events: manage`, confirmed first, and removes the object and then its row. **Photo objections:** when any active registration of the event has `photo_consent = false`, the card says how many people objected — a count only — and asks the reader to check photos and footage before sharing them outside the portal. **Usage:** the card shows the bytes stored for the event and for the tenant's event media. Uploader name, both sums and the objection count come from `uploader_name(event_media)` and `event_media_summary(event_id)`.

**Per-tenant setting: Event media uploads**, `events.media_uploads_enabled` in `app_settings`, on when there is no row, switched from the **Media** button on the Events page at `events: manage` (`set_event_media_uploads_enabled`). Off hides the upload control and refuses uploads in the bucket policy; what was uploaded stays.

**Per-tenant setting: Keep photos and videos** (#1608), `events.media_retention_days` in `app_settings`: a number of days after the event (the sheet offers 30 days to 5 years; `set_event_media_retention_days` takes 30–3650), or no value to keep media indefinitely. There is no default: nothing expires until a tenant picks a period. Set from the same **Media** sheet at `events: manage`. A file expires at the event's end (its start when it has none) plus the period, but **never sooner than 14 days after the setting last changed or the file was uploaded** — `event_media_expiry()` is the one rule, read by `expires_at(event_media)`, `event_media_event_expires_at(event_id)` and `expired_event_media(now)`. The two floors make the Media card's warning a guarantee: the card lists every file that expires within 14 days, with its date and a download, so picking a short period on a tenant with old footage, shortening it, or uploading to a long-past event never deletes anything unannounced. The card's storage line says how long the event's media is kept and until when.

**Purge** (#1608): the daily `/api/cron/storage-purge` run sweeps the bucket after its other five. It deletes objects with no `event_media` row once they are a day old (abandoned or failed uploads; the row set is read first and a failed read stops the run — a row's `thumb_path` counts as referenced too), then the files `expired_event_media()` returns, object and thumbnail first and then row. A tenant without a period has nothing expired.

**Upload links** (#1620): a photographer or videographer with no portal account uploads through a link a coordinator sends them, rather than through a Drive folder somebody re-uploads by hand. The link is a single-purpose capability, not a sign-in.

- **Managed from the Media card** at `events: manage` (shown only where the reader can upload and is not on the demo tenant). **Create upload link** takes who it is for (the label, e.g. "Sam — photographer"), an expiry date (end of that day in the coordinator's zone; defaults to 7 days after the event ends, its start when it has none; at most a year out) and a storage limit (default 50 GB, 1–1024). The URL is shown once, with **Copy** and a QR code — only the token's SHA-256 is stored. The card lists the event's links with status (active, expired, revoked), expiry, and the files and bytes uploaded through each; **Revoke** stops new uploads and leaves what was uploaded. Emailing the link from the card is not built yet.
- **The page** is `/portal/media-upload/<token>` (shown as `/media-upload/<token>` on a `portal.` host), outside the portal's signed-in group so it resolves on every host shape, including the platform tenant's portal-only one; it is `noindex` and `no-referrer`. It shows the tenant's logo, the event's name and date (in the event's zone, labelled), who the link is for and when it expires — no registrant data and none of the event's existing media. Every dead link — unknown, expired, revoked, another host's tenant, the demo tenant, uploads turned off, event deleted — is one `LINK_INVALID` message, from `resolve_event_media_upload_link()`.
- **Rights.** Before the picker opens, the uploader ticks a box scoped to the files: "These photos and videos are mine to share, and I agree to the terms above" when the tenant has written `events.media_upload_rights` (Site Content → Events → Photo and video upload links), shown above the box; otherwise "…and <org> may keep them with this event". Each row snapshots the paragraphs (`rights_terms`) and the time (`rights_confirmed_at`), from `site_content` and never from the client, as `artwork_submissions.consented_terms` does. It is not a site-wide terms acceptance (#1318). The slot ships blank; Chatter Snow's is seeded from its own published photo and terms paragraphs.
- **Originals.** Photos uploaded through a link are stored byte for byte at full resolution (HEIC, which the bucket cannot store, is converted to a full-size JPEG), with a 2048px JPEG thumbnail at `{uuid}-thumb.jpg` beside each for the gallery; downloads and the .zip use the original. Video goes up by resumable upload as from the portal. The page lists only what it has uploaded since it was opened, and each of those files can be **deleted until the page is closed** — by a receipt the page holds in memory, whose hash is on the row.
- **Server side**, the artwork-submissions pattern (technical spec §7): no `anon` policy on `storage.objects`. `claim_event_media_link_upload_slots()` (60/15min per IP) checks the link and the byte cap against what has been recorded plus the batch's declared size, then the Server Action mints signed upload tokens with the service-role client for paths it chooses. `record_event_media_by_link()` re-checks the link, that the path is the link's tenant and event, reads type and size off the object, re-checks the cap against the real size, and inserts the row with `upload_link_id` set and `uploaded_by` null; `uploader_name()` returns "<label> (upload link)". An upload never recorded is an orphan for the daily sweep; retention applies as to any other file.

**Public gallery** (#1654): photos go into the event's public gallery automatically; videos do not until someone marks them public.

- **`event_media.is_public`**, set on insert by a trigger from the content type — photos true, videos false — whatever the caller sent, through the portal and upload links alike. Changed only by `set_event_media_public(ids, public)` at `events: manage` (the column has no update grant). The Media card shows a **Public** / **Not public** badge on every item; `events: manage` hides or shows one, or the ticked photos together.
- **Per-tenant setting: Public event gallery**, `events.public_gallery_enabled` in `app_settings`, on when there is no row, from the same **Media** sheet at `events: manage`. Off, nothing is public whatever it is marked, and the card says so. Chatter Snow is seeded on.
- **The public read** is `public_event_media(tenant_id, event_id)`, service role only: the public rows of a public, published event of that tenant while the setting is on, newest first, with the path to sign (a photo's thumbnail where it has one) and never the uploader, filename or link. The server takes the tenant from the request host and signs hour-long URLs; nothing else leaves it.
- **Pages.** The event page (`/events/e/<id>`) previews the newest 8 photos and the public videos under a **Photos** heading, with a **Photos (N)** link under the date and **View all photos** at the end; both hidden with nothing public. `/events/e/<id>/photos` is the whole gallery and the shareable link; it renders not-found unless the event is public and published, the setting is on and something is public. The Media card offers that link with **Copy link** in the same cases, absolute on the tenant's public domain from a `portal.` host.
- **Takedown.** Both pages render on every request, so hiding or deleting an item — or the retention purge — removes it from the next one; a signed URL already handed out lasts its hour. With the gallery on, the card's photo-objection notice says photos are public as soon as they are uploaded.

### Registration options

**One optional single-choice question per event** (issue #1407) — a prompt and an ordered list of up to ten options, such as Chatter Snow's "I'll use my own / I need a ticket / I need a ticket and gear", or "bring my own mat / need a mat" for anyone else. The platform knows nothing about what an option means. An event with no options asks nothing and behaves exactly as before.

**Answered per person as counts.** Where an event has options, both registration forms, the public API and `register_for_event()`/`register_myself_for_event()` (`p_option_counts`, an object of option id → count) require counts that add up to `party_size`; party members are not named. Refusals are `EVENT_OPTIONS_REQUIRED`, `EVENT_OPTIONS_MISMATCH` and `EVENT_OPTIONS_INVALID`, and a refused answer rolls the registration back with it.

**An option may be capped** (10 sponsor tickets, 6 gear sets). A cap is enforced under the same `for update` lock on the event row as `events.capacity`, taken before the registration insert, so concurrent registrations cannot oversubscribe it; a full option is refused with `EVENT_OPTION_FULL` and shown as full on the form (the public view exposes `is_full`, never the counts), while the others stay open. Only an increase is refused, so a registrant keeping what they hold is never turned away. **Staff are not capped**: the portal's add-registrant and walk-in dialogs record counts through `set_registrant_option_counts()`, optional and uncapped, as `events.capacity` is not enforced on them either.

**Set up on the event's Planning tab** beside capacity, through `save_event_registration_options()` (add, rename, reorder, remove, cap, and since #1589 price). A tenant's defaults in `app_settings` key `events.registration_option_defaults` (`{"prompt": …, "options": [{"label": …, "cap": …}]}`) are copied onto every new event by an insert trigger and are then the event's own. Chatter Snow's are seeded (`20260923110000`).

**Answers keep their words.** Each count row copies the option's label as shown; renaming an option leaves old answers alone, and removing one keeps its counts with a null `option_id`.

**Where they show:** a column and per-option totals against caps on the registrants tab, the registrant sheet, the confirmation email ("Your choices"), `GET /events/{event}` (`registration_options`), and `/my/registration/[id]`, where a linked registrant can change their answer through `set_my_registration_option_counts()` while registration is open — held to the same sum and caps.

**In the registrants list (#1512)** each top-level question is one column, headed by its optional `column_label` ("Carpool") or, without one, its prompt cut to 24 characters with the whole prompt as a tooltip. A conditional follow-up has no column of its own: its answer follows its parent's in the same cell, with its label as the unit ("Can drive · 2 seats"); a conditional consent box keeps its own column, since "Yes" means nothing after another answer. Cells hold the answer alone, on one line, cut with a tooltip. The registrants page shows the first three columns until the reader picks others in its Columns menu (`cols` in the URL), and offers a filter per shown choice or consent column (`ans`). Full prompts and answers stay in the registrant sheet, where follow-ups are indented under their parent, and in the CSV, which is unchanged. The logic is `src/lib/registration-answer-columns.ts`.

Out of scope: gear sizing (the rider profile add-on, #1408), named party members, payment.

### Registration questions

**Zero or more typed questions per event** (issue #1501), each with a prompt, optional help text, `required` and a place in the event's order. Six kinds and nothing more general: `single_choice` and `multi_choice` (with options), `short_text` (up to 500 characters), `number` (a whole number, with an optional min and max), `consent` (a declinable box in the tenant's own words) and `place` (a city, town or neighborhood picked from a list, #1699 — see "Place questions" below). Carpooling is Chatter Snow's first use — "Getting there", "Seats available", "Leaving from", "OK to share my name and contact with the partner" — and the platform knows nothing about what a question means. An event with no questions asks nothing and behaves exactly as before. The kind vocabulary and validator live in `src/lib/registration-questions.ts` so per-person profile questions (#1409) can reuse them.

**Answered once per registration**, unlike "Registration options" above, which are counts per person: a party travels together. Both registration forms ask them on step 2 ("This event") and show them on the review step; the public API takes them as `answers` on `POST /registrations` (question id → answer) and `GET /events/{event}` exposes `registration_questions`. `register_for_event()`/`register_myself_for_event()` (`p_answers`) validate every answer server-side through `apply_registration_answers()` and refuse with `EVENT_ANSWERS_REQUIRED` or `EVENT_ANSWERS_INVALID`; a refused answer rolls the registration back with it, as option counts do.

**Conditions are one level deep.** A question may be shown only when an earlier single-choice question has one of given answers (`show_if`, e.g. "Seats available" only after "Driving, can offer seats"). A question shown only conditionally cannot be a condition itself. A hidden question is neither required nor stored, whatever a client sends for it.

**Sharing with a partner is a `consent` question, never implied by registering** — the #1318 rule in [`docs/legal-basis.md`](../legal-basis.md#what-submitting-a-public-form-means). A consent question marked `shares_contact` is the one the answers export reads; an unticked box is stored as the answer "no", not left blank.

**Answers keep their words.** Each answer row copies the prompt (`prompt_as_shown`) and the answer as shown (`answer_text`: the option labels, the text, the number, or Yes/No) beside the raw `value`, so editing a question never rewrites an old answer, and every reader shows the copy. A question removed while it has answers is **archived, not deleted**, and its answers stay readable beside the registration; one with no answers is deleted.

**Staff are not held to `required`**, as they are not held to option caps: the add-registrant and walk-in dialogs and the registrant sheet record answers through `set_registration_answers()` (`events: manage`), all optional, so an organizer records what they know.

**Set up on the event's Planning tab** through `save_event_registration_questions()` (`events: manage`): add, edit, reorder, archive and set a condition. There is **no tenant default**, unlike options' `events.registration_option_defaults`: questions are specific to an event and its partners, so the editor instead offers **copy questions from another event**, which brings that event's questions in as new questions of this one, to be edited and saved as its own.

**Where they show:** answer columns and a "missing required answers" filter on the registrants tab and page, the registrant sheet (editable by staff), the confirmation email ("Your answers", the prompts and answers as shown, in order), and `/my/registration/[id]`, where a linked registrant can change their answers through `set_my_registration_answers()` until the event ends while their registration is active (since #1591; it closed with registration before, but changing an answer takes no place) — held to the same rules as registering, required questions included. That card is also how somebody who registered before the questions existed completes them: it says so when a required question is unanswered.

**Export: "Download answers (CSV)"** on the registrants toolbar, gated by `events: manage` — the first registrants export. Columns are name, party size and one per question, the Instagram handle on every row that has one, plus email and phone **only on rows whose `shares_contact` consent was ticked**; a registrant who declined, or an event with no such question, exports no email or phone. The Instagram handle is outside that consent by the organization's choice: it is a public handle given so the organization can tag and find the registrant. For a reader who also holds `rider_profiles: view` (so only where the `rider_profile` module is on), the file adds Rides, Ski level and Snowboard level after the questions — not contact details, so not under that consent — read like the Rides column: the check-in snapshot first, the person's profile otherwise. The export is offered whenever the event has questions or the reader sees rider answers.

**Riders breakdown.** For the same reader, the registrants page shows a Riders section under the summary — how many registrations ski, snowboard or both, and the beginner/intermediate/advanced split for skiers and for snowboarders (someone who does both counts in each) — and the event's registrants card adds it as one line. Counted per registration, not per head: the rider answers are the registrant's own. The logic is `src/app/portal/(app)/events/rider-stats.ts`.

**Retention.** Answers are personal data — free text can hold an address — so rule C of the retention purge ([§7.11](../technical-spec.md#711-retention-deletion-export-and-access-procedures)) **deletes** a registration's answers when it anonymizes the registration three years after its event. Deleted rather than blanked: an answer with its value removed says nothing, and a consent to share contact details is worthless once the row cannot be tied to a person.

Out of scope: per-person profile questions (#1409), conditions deeper than one level, and file uploads.

#### Place questions

**A `place` question is answered from a list, not typed** (issue #1699, part of #1698), so "bk", "Brooklyn" and "wburg" stop being three answers that cannot be grouped, counted or matched for carpools. Both registration forms, the answers link (#1591), `/my/registration/[id]` and the staff dialogs show an autocomplete (`PlaceCombobox`, shadcn `combobox`) that searches after the second letter; labels say as little as tells places apart — "Williamsburg, Brooklyn", "Montclair Twp, Essex Co., NJ", "Washington Twp, Morris Co., NJ". It is a platform feature: any tenant in the US gets a usable picker with nothing configured.

Each question has two settings in the editor:

- **Granularity**: **City/town** (`locality`: a city, town, township, village, borough or CDP; in NYC, one of the five boroughs) or **Neighborhood where available** (`neighborhood`: an NYC neighborhood — a residential 2020 NTA — or a neighborhood loaded for another city, and the city/town list everywhere else, which is the fallback).
- **Allow "Not listed"**, on by default: picking it reveals a text field of up to 200 characters, so nobody is blocked by a place the list does not have.

**Storage.** The answer is `{"place_id": uuid, "label": "<as shown>"}` or `{"other": "<text>"}`, and `answer_text` is that label or text. `apply_registration_answers()` refuses a `place_id` that is not a place of a kind the granularity allows (a neighborhood to a city/town question, a state or county to either) and `other` where "Not listed" is off, and it copies the label **from the place**, ignoring whatever label the client sent. Answers keep their words, so updating the places dataset never changes an old answer. A `place` question cannot be a `show_if` condition, since only single-choice questions can. The registrants list, the answers export and the answers link show the label.

**Where registrants come from** (issue #1701). Every count is derived from answers on registrations that were not cancelled, never typed. A place's **region** is the county or NYC borough it lies in, or its state where the Census gives it no county; a county, borough or state is its own region — one definition, `place_regions()`, which every surface below groups by. An answer counts under its stored `place_id` while that place exists; "Not listed" text, or an id the dataset no longer has, counts as Other.

- **Event detail** gets a **Where registrants come from** card in the rail's Guests group, listed only on an event with a current place question: per question, registrations by region and then by town or neighborhood (a borough picked at city/town granularity shows as "nothing more specific"), plus Not listed. Read through `get_event_place_breakdown(event_id)` (security definer; `events: view` or `event_impact: view`). Small counts are shown: it is a staff view.
- **The Results card's Outcomes** gain **Reach** — distinct places reached and the regions they lie in — and the **Program Impact Report** a **Places reached** row and a by-area table, through `get_program_place_reach(program_id)` (`programs_reports: view`). The sentence to quote outside ("Registrants from 23 places in 2 boroughs and 1 county: 14 in Bronx, NY, …") is totals only and names a region only when at least two registrations came from it (`placeReachSummary()` in `src/lib/places/place-breakdown.ts`).
- **Carpools and the registrants page** filter a place column by region, plus Not listed, and sort it by region then place, so riders from one area sort together.

**Finding a place** (issue #1700). Besides its name, a place is found by:

- **A ZIP.** Five digits list the places that ZIP covers, from `place_zips`; the registrant picks one, because ZIPs cross municipal lines and an NYC ZIP spans several neighborhoods. At neighborhood granularity an NYC ZIP lists its NTAs ahead of the borough; otherwise places rank by the share of the ZIP's land they cover, service area first. A ZIP is never an answer and is never stored: the answer is the place picked. The service area picker (`area`) finds nothing for a ZIP.
- **An alias**: a section of a city or a post-office name that is not a place of its own, kept in `places.aliases` — Ironbound and Down Neck → Newark, Journal Square and Paulus Hook → Jersey City, Bayville → Berkeley Twp. The list shows **"Ironbound (Newark, Essex Co., NJ)"** so the registrant sees why it came up, and the answer is the municipality's own label. NJ's aliases are hand-curated in `scripts/places/aliases.ts`; most post-office names (Short Hills, Princeton Junction) are Census CDPs and are found on their own, and a unit test refuses an alias that already names a place in the state. NYC's borough and NTA aliases from #1699 show the same way ("Kings (Brooklyn, NY)").
- **"Township" or "borough" spelled out.** Labels abbreviate them ("Toms River Twp"), so the search treats _township_/_twp_ and _borough_/_boro_ as the same word.

**Neighborhoods for other cities** are loaded on demand, one city at a time, for a city a tenant's service area includes — never the whole US — with `bun run places:neighborhoods <place key> <WOF locality id>` (`scripts/places-neighborhoods.ts`, rules in `scripts/places/wof.ts`). It reads the city's current Who's On First neighbourhood and macrohood records and writes a new migration adding them as `neighborhood` rows under the city, labelled "<name>, <city's label>" ("Germantown, Philadelphia, PA"). WOF is mostly CC0, but the license is checked **per record**: only records whose source (`src:geom`) is on the CC0/public-domain list in `wof.ts` are loaded, and the run prints what it left out and why (for Philadelphia, most records come from Azavea, which requires attribution, and are left out). A CC-BY source may be added to that list only together with a credit wherever the platform lists data credits — there is no such page yet, because nothing loaded needs one. NYC keeps its NTAs; NJ stays county → municipality, with its sections as aliases (#1698). **No city has been loaded yet**: Chatter Snow's service area is NYC and NJ.

**The service area** is a tenant setting in the **Registration** sheet on the Events page (`registration.service_area` in `app_settings`, through `set_registration_service_area()`, `events: manage`): up to 50 states, counties and boroughs. Places inside it rank first in the autocomplete; places outside it can still be found; with none set the whole US ranks equally. The public form never sees the list directly — `searchPlacesAction` reads it from `public_registration_settings` on the server, where the request host resolves the tenant. Chatter Snow's is the five boroughs and New Jersey (set by migration `20261023160200`). Its 5Borough "Borough" question (#1512) was created in the editor, so staff switch it to `place` there, not a migration: open the event's Planning section, change the question's **Answer type** to **Place (city, town or neighborhood)**, leave **Granularity** on **City/town** and **Allow "Not listed"** on, and save. Answers already given stay as typed text on their registrations.

**The places dataset** (`places`, platform-wide, see the data model below) is our own reference table, seeded from public data; no third-party API is called at runtime, so a registrant's keystrokes never leave our system and the picker costs nothing. `bun run places:seed` (`scripts/places-seed.ts`, row logic in `scripts/places/build.ts`) downloads the sources and regenerates migration `20261023160100_places_seed.sql`; a newer vintage is a new seed migration. Sources and vintages:

| Source                                                                                          | Vintage | What it gives                                                                                                                                                                      |
| ----------------------------------------------------------------------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| US Census Bureau, Gazetteer files: counties, county subdivisions, places                        | 2025    | Counties, cities/towns/townships/villages/boroughs and CDPs, with GEOIDs. County subdivisions that are statistical (CCDs, unorganized territories) or nonfunctioning are left out. |
| US Census Bureau, FIPS codes: states; places by county                                          | 2020    | State names; which county a place lies in (the Gazetteer has no county for a place). Connecticut's places get no county, since its counties became planning regions in 2022.       |

| NYC Department of City Planning, 2020 Neighborhood Tabulation Areas (NYC Open Data `9nt8-h7nd`) | 2020    | NYC neighborhoods; non-residential NTAs (parks, airports, cemeteries, other special use) are left out.                                                                             |

Rules the seed applies: a Census name's suffix becomes `place_type` ("Montclair township" → Montclair, `township`), and a label adds "Twp", "Boro", "Village" or "Plantation" where that tells two places apart; a county subdivision that is the same municipality as a place in its county collapses into the place, and a CDP named like the municipality around it is dropped; NYC's five counties become `borough` rows with "New York", "New York City" and "NYC" as aliases, and NYC itself is not a separate place. NJ labels always name the county; elsewhere the county appears only where a name repeats in the state. NJ municipalities are checked against the NJ Office of GIS count, **564** (since Pine Valley merged into Pine Hill in 2022): the build fails on any other number. Ids are uuid v5 of each row's source key (`place_key_id()`), so a rebuilt seed keeps an unchanged place's id.

`bun run places:overlays` (`scripts/places-overlays.ts`, row logic in `scripts/places/zips.ts`) regenerates migration `20261024120100_places_overlays.sql`: the ZIP rows and the aliases, checked against the seed migration so it names no place the seed lacks. A ZIP maps to a place covering at least 5% of the ZIP's land, or a place at least half inside the ZIP (a small borough in a large rural ZIP). A rebuilt seed must be followed by a rebuilt overlay.

#### Asking for missing answers by emailed link

**Questions added after registrations opened leave earlier registrants with nothing answered** (issue #1502), and most of them have no account, so `/my/registration/[id]` does not reach them. Staff email each one a link instead. **The link is a single-purpose capability, not a sign-in:** it opens a public page, `/events/e/[id]/answers?t=<token>`, showing the event's name, the registrant's first name and **only that event's questions**, prefilled with any answers already given — no email, phone or party details, so a forwarded link leaks almost nothing. Saving goes through `apply_registration_answers()` with the same rules as registering, required questions included, and the link can be used again to correct an answer until it expires. A linked registrant gets the same link; there is no special case.

**Sending.** "Ask for missing answers" sits beside "Message registrants" on the registrants tab (`events: manage`) whenever some active registration is missing a required answer. The dialog counts the active registrations missing at least one required answer that have an email address, previews the email (subject, an editable intro, the link) and mails each its own link — at most 50 per send, the announcement cap; the rest are picked up by sending again. It **skips anyone asked in the last 24 hours** unless "Include anyone asked in the last 24 hours" is ticked. The registrant sheet has the same action for one registration ("Ask for answers", beside "Resend confirmation"), sent while the staffer waits. The links are written before the response, so a link works as soon as it arrives; the bulk mail goes out after it, and each send is recorded in that registrant's message history (kind `registration_answers_request`). A send that fails withdraws its link, so the tab never says "Asked" for somebody who was not.

**Status.** The registrants tab shows "Asked {date}" or "Answered" under a registrant's name: answered once answers have been saved through a link since it was last sent.

**The token** follows #1049's confirmation tokens: 32 random bytes minted in the Server Action; only the SHA-256 is stored, in `event_registration_answer_requests`, and that column is withheld from the select grant because the public functions accept a hash. **Expiry is the event's end**, or its start plus a day where it has none — independent of the registration deadline, because answering takes no place — and a cancelled registration's link stops working at once. Asking again supersedes the earlier link. **Unknown, expired, superseded, cancelled and other-tenant links all show the same "this link no longer works — contact us" page** (`LINK_INVALID`), so they cannot be told apart. The page sends `Referrer-Policy: no-referrer` and `noindex`, and renders the token into its form rather than into any link. Both public functions are rate-limited per `(route, ip_address)`.

Out of scope: automatic reminders on a schedule, and SMS.

#### Registrants changing their own answers

**Every registrant gets the link, without anyone asking** (issue #1591). A registrant whose plans changed had no way to say so but to register again under a second address, which inflated the headcount and left two sets of answers that disagreed. So wherever the event asks questions:

- **The confirmation email** carries a "Change your answers" link to the same capability page, with when it stops working in the event's own zone. So does every staff "Resend confirmation", each with a fresh link.
- **The success screen** shows the same link as a button, so the registrant has it without opening the email.
- **"Already registered" is a way forward.** Registering again with an address that already has an active registration for the event mails that address a fresh link and says "You're already registered — we've emailed you a link to change your answers." The link is never shown on screen, so typing somebody else's address reveals nothing the refusal did not already. It is rate-limited per `(route, ip_address)`, 5 per 15 minutes, separately from registering. An event with no questions, or one that has ended, keeps the plain refusal.
- A signed-in registrant keeps `/my/registration/[id]`; the emailed link works for them too.

**Issued only on the server.** The Server Actions mint the token and call `issue_registration_answer_link()` or `issue_registration_answer_link_for_email()`, both executable by `service_role` alone: the caller supplies the hash, so anyone who could call them could hold a working link. Neither issues anything for an event with no current questions, a cancelled or nonexistent registration, or an event that has ended.

**One live link per registration.** The table stays one row per registration, so each link supersedes the one before, whoever issued either — a staff ask kills the confirmation's link, and a resend kills a staff ask's. The newest email always works, and the "no longer works" page tells the reader to use the most recent email from the organization. That was chosen over several live links as the simpler of the two.

**What staff see.** `event_registration_answer_requests.source` (`staff | confirmation | already_registered`) says who issued the current link, and only a staff ask reads as "Asked" or counts toward the 24-hour "recently asked" guard. `event_registrations.answers_changed_at` records when the registrant last changed their own answers after registering, through the link or `/my` (never a staff edit). It shows as "Answers changed {date}" under the name on the registrants tab, "Changed by the registrant on …" in the detail sheet, and an "Answers changed" column (UTC, ISO 8601) in the answers CSV. Staff are not emailed about a change.

Out of scope: self-cancellation for anonymous registrants through the same link, and fuzzy duplicate detection across different addresses.

### Cancelling a registration

**Cancelled, not deleted** (issue #1418). `event_registrations` carries `cancelled_at`, `cancelled_by`, `cancellation_reason` (`not_attending | mistake | duplicate | other`) and an optional staff `cancellation_note`. The row stays, so history, "been before" and claim-from-registration keep reading it.

**What a cancellation frees.** Both registration RPCs sum only active rows against `events.capacity`, and `apply_registration_option_counts()`, `public_event_registration_options.is_full` and `my_registration_option_counts()` sum only active rows against an option's cap; the counts themselves are kept. A discount code reserved for the registration is released back to the pool, unless it was already sent. The one-per-person and one-per-email unique indexes cover active rows only, so somebody who cancelled can register again. A check constraint keeps a registration from being both cancelled and checked in.

**Who cancels.** Staff with `events: manage` cancel from a row action on the Registrants tab, with a reason and a note (`cancel_event_registration()`), and optionally email the registrant. Cancelled rows sit behind **Show cancelled**, where staff can **Restore** them (`restore_event_registration()`). A restore is refused if the seats (`EVENT_AT_CAPACITY`) or an option's cap (`EVENT_OPTION_FULL`) have been taken since, or if the person has registered again (`ALREADY_REGISTERED`). A linked registrant cancels their own registration with **I can't make it** on `/my` or on the event page, until the event starts (`cancel_my_event_registration()`, `EVENT_ALREADY_STARTED` after). That records the reason as `not_attending` and sends them a "your registration was cancelled" email, which is recorded in the registration's message history.

**Where it drops out.** Cancelled rows are excluded from check-in, announcements, one-to-one registrant messages and resent confirmations, the tab's counts, option totals, the portal home and calendar-preview figures, the "still to check in" attention item, and the impact RPCs' registration lists. `/my` and the person record's attendee card list them marked **Cancelled**.

Hard delete is unchanged: the `event_registrations delete` policy (`events: manage`) stays, and nothing in the application uses it. Out of scope: waitlist promotion and refunds.

### Group chat

**A per-event switch** (issue #1648). An organizer that adds its registrants to a group chat for the event, as Chatter Snow does on Instagram, turns on **This event has a group chat** on the event's Planning section, with an optional name of up to 40 characters ("Instagram group chat"; blank reads "Group chat"). Off, nothing below shows anywhere, and turning it off keeps the flags.

**Every registrant, carpool or not.** On the registrants card and the registrants page a column named for the chat shows **✓ {date}** or **Not added**, beside the Instagram handle staff copy into it. The page adds an Added / Not added filter (`chat=added|not-added` in its URL), a tick box on each row with **Mark added to {chat}** / **Mark not added** for the ticked rows, and the same toggle in each row's menu; the card adds a "{chat}: not added" toggle that carries over to the page. The detail sheet shows "Added {date} by {staff name}" with the toggle. Marking a row already in that state keeps its date and name.

**Cancelled registrations keep their flag** and so drop out of "Not added". **Show cancelled** marks them "Still in {chat}", counts them on its toggle, and offers **Removed** to clear the flag once staff have taken them out.

**Staff only.** Read at `events: view` with the rest of the row and written at `events: manage` through `set_registrations_group_chat(event, registrations, added)`, which refuses an event in another tenant (`EVENT_NOT_FOUND`), an event with the switch off (`GROUP_CHAT_DISABLED`), and the whole call if any registration is not the event's (`REGISTRANT_NOT_FOUND`). No registrant-facing surface reads it, so it is not a promise to them. Not audited per toggle: like an answer it is an operational flag, and `group_chat_added_by` records who set it.

### Carpools

**A per-event switch** (issue #1649, part of #1646). Registration questions tell staff who can drive and how many seats they have (#1501); the plan itself -- which car, who drives, who rides with whom, and who has paid their driver -- lives with the event once staff turn on **Organize carpools** on its Planning section. Off, nothing below shows anywhere, and turning it off keeps the cars. Beside the switch, **Seats come from** optionally names one of the event's `number` questions ("Seats available").

**The board** is its own page, `/portal/events/[eventId]/carpools`, reached from the **Carpools** card in the event's rail (Guests), which summarizes cars, seats taken, unassigned and unpaid. A card per car shows its label (default "Car 1", "Car 2", ...), its driver or a **No driver** flag, "{used} of {seats} seats", "{paid} of {passengers} paid", the leaving-from (shown to the car since #1651) and the staff-only notes (each up to 500 characters). Below them, **Unassigned** lists the active registrations in no car with the event's answer columns, search and answer filters (the registrants page's, so "Need a ride" is one filter away), and an **Add to car** select.

- **Cars.** Staff add and edit a car with a label, a driver chosen from the active registrations in no car, seats for passengers (a whole number from 1 to 12, prefilled from the driver's answer to the seats question when the event names one, otherwise typed), leaving from and notes. Deleting a car sends its passengers back to Unassigned.
- **Seats.** A registration takes seats equal to its party size, because a party travels together. A car over its seats is warned about ("over capacity") but still saves, because staff may know better.
- **One car each.** A registration is in at most one car per event, as its driver or as a passenger, never both. Passengers move between cars, or back to Unassigned, from their row.
- **Payment.** Each passenger has a **Paid driver** tick with the date and who marked it. No amount is stored: riders work out the split with their driver (#1646). Moving a passenger to another car clears the tick, since the driver changed. **Unpaid** filters the board to the passengers still to pay (`paid=unpaid` in its URL).
- **On the registrants.** The registrants card and page gain a **Carpool** column ("Car 2 · Driver", "Car 2 · Passenger · Paid", "Unassigned"), and the detail sheet the same line, linking to the board.
- **When things change.** Cancelling a registration, on any path, takes it out of its car; a driver's car keeps its passengers and shows **No driver**. Undoing the cancel does not put it back. When a registrant changes their answers after being put in a car (#1591), their row on the car card says "Answers changed {date}".
- **The cost-split notice** (#1650). Wherever carpooling comes up on an event with carpools on -- registration step 2 under the event's questions, the review step, the confirmation email, and the assignment card and email (#1651) -- registrants are told that costs are split in the car and settled with the driver, that the organization does not collect them, and that the people in their car see their first name and Instagram handle. It is the `events.carpool_cost_notice` slot (Site Content → Events → Registration), with a platform default in the organization's voice and Chatter Snow's copy seeded; one component (`CarpoolCostNotice`) and one email partial render it. Notice only: no box, and nothing is stored about having seen it (`docs/legal-basis.md`). With carpools off it never shows.
- **Export.** **Download carpools (CSV)**, at `events: manage`: car, role, name, party size, Instagram handle and paid, one row per person in a car with the driver first. Email, phone and the preferred contact detail follow Download answers' consent rule (#1501, #1647): their columns exist only where the event has a `shares_contact` question, filled only on the rows that ticked it.

**What registrants see** (issue #1651). A **Your carpool** card shows a registration in a car its car label and leaving-from, their role (driving or a passenger), the driver's first name and Instagram handle -- or "No Instagram — ask {Organization} to connect you" -- the other riders' first names and handles with party size where it is over 1, and the cost-split notice. A registration on a carpool event that is in no car yet sees "You haven't been placed in a car yet" (the platform cannot tell which answer means "needs a ride", so every unplaced registrant sees it); events with carpools off show no card. **Phone numbers, emails, the preferred contact detail, staff notes and paid status never reach a registrant**: `carpool_assignment_card()` builds the card and returns nothing else. The card is on the answers link page (`/events/e/[id]/answers?t=…`, through `registration_carpool_by_token()`, with the link's `LINK_INVALID` handling) -- the primary surface, since most registrants, and every Chatter Snow registrant, have no account -- and on `/my/registration/[id]` for linked registrants (`my_registration_carpool()`), beside the answers and "How we reach you" cards. An event with carpools on issues the answers link at confirmation even when it asks no questions.

**Email carpool assignments** on the board (`events: manage`) sends each driver and passenger the same contents as the card and a fresh answers link, which replaces their earlier one (#1591: the newest email always works). It sends to everyone, or only to those whose car changed since they were last emailed: `event_carpool_assignment_emails` keeps when each person was last sent their card and an md5 of it, so a new car-mate, a new driver, a renamed car or a changed handle all count as a change. Who is sent is resolved by `event_carpool_assignment_recipients()`; the mail goes after the response, each send is logged in that registrant's message history as **Carpool assignment**, and the dialog reports how many it is sending to, as #1502's does. Leaving-from is shown to the people in the car; notes stay staff-only.

**Staff only.** Read at `events: view`; written at `events: manage` through `save_event_carpool_car()`, `delete_event_carpool_car()`, `set_event_carpool_passengers()`, `move_carpool_passenger()` and `set_carpool_passenger_paid()`, each of which refuses an event with the switch off (`CARPOOLS_DISABLED`), a car or registration of another event or tenant (`CAR_NOT_FOUND`, `REGISTRANT_NOT_FOUND`), a cancelled registration (`REGISTRANT_CANCELLED`) and a registration already in a car (`CARPOOL_ALREADY_ASSIGNED`). Car create, delete and driver changes are audited like the event's questions; passenger moves and paid ticks record who and when on the row only. Out of scope: matching riders to drivers automatically, registrants choosing their own car, and collecting or splitting payments in the app.

### Event reminder

**A per-event switch** (issue #1652). A registrant on a tenant without accounts finds their registration again only through an emailed link (#1591), and by the event the newest one is weeks old. **Reminder email** on the event's Planning section, on by default for new events (events that existed before it shipped were left off), sends every active registration with an email address one reminder **N days before** the event (default 2, from 1 to 14), at **09:00 in the event's own zone**: `event_reminder_send_at()` takes the event's local start date, subtracts the days and pins the morning, so the hourly cron lands within the hour of it wherever the event is. An optional **Reminder intro** of up to 1,000 characters opens it, prefilled with the platform default; saved blank or unchanged it is stored as null and reads the default. Planning shows **Scheduled for {date} · {n} recipients** (the date in the event's zone, labelled), then **Sent {n} of {total}** while the rest wait for a later run, and **Preview reminder** renders it for a made-up registrant.

**The email** (`src/lib/notifications/event-reminder-email.ts`) carries the event's name, when (labelled in its zone) and where; on an event with carpools on, **Your carpool** with the same lines and privacy as the assignment email (#1651) and the cost-split notice (#1650), or "You haven't been placed in a car yet"; a **fresh answers link** (#1591's rule, widened by #1647 and #1651, source `reminder`), which replaces the one before it; and on a tenant with `constituent_accounts` on, a `/my/registration/[id]` link as well. It is the `event_reminder` kind, not a notification kind (#1502's reason), governed by the organization's email switch, and logged in the registration's message history as "Event reminder, sent automatically" or "…, sent by {name}".

**Once per registration.** `/api/cron/event-reminders` runs hourly (`vercel.json`, `CRON_SECRET` like the other cron routes). `claim_event_reminders(tenant, limit)` stamps `event_registrations.reminder_sent_at` on the due rows **before** anything is sent, under `for update skip locked`, so a retried or overlapping run sends nothing twice; the delivery ledger's dedupe key is the second lock. Due means a published, reminder-on event whose send time has passed and whose start has not, and an active registration with an email made **before** the send time — registering later sends nothing, because the confirmation is close enough. Cancelled registrations, and events cancelled before the send time, get nothing. A failed send stays stamped and logged as "Not sent", so staff can send it again. Tenants with Events or email off claim nothing.

**Sending limits.** Outbound mail goes through Resend, on the free tier (100 a day, 3,000 a month, shared with every other email). Each run sends at most `EVENT_REMINDER_DAILY_LIMIT` (default 100) less the reminders sent in the last 24 hours, oldest send time first; a larger event finishes over later runs, which Planning's status line shows. On Resend Pro ($20 a month, 50,000 a month, no daily cap) raise the variable.

**On the registrants.** A "Reminder sent {date}" badge under the name on the registrants card and page, and in the detail sheet **Reminder email: Sent {date}** or "Not sent" with **Send reminder now** at `events: manage` (`stamp_event_reminder()`), which sends it at once — again if it already went — and stops the job sending it later.

The "Do you ski or snowboard?" questions on registration's second step, its door-side counterpart on the registrants tab, the "What you ride" group on `/my/details`, the rider fields on the person record and form, and the Impact "Beginner participants" figure are one add-on, the `rider_profile` module (#1408). ### Sponsor and partner selection

Event sponsors/partners are people or organizations that already live in the shared `people` directory (the same table backing donors and volunteers, see [§6](../technical-spec.md#6-proposed-data-model)) rather than free text typed per event. Managing an event's sponsors shall work as follows:

1. The event editor's Sponsors tab provides a type-ahead search (matching on name and email) over `people`. Staff pick an existing person/organization from the results to link them to the event.
2. If no existing record matches, the same control lets staff create a new `people` record inline (name required; email, phone, and notes optional) and link it to the event in one step, without leaving the event editor.
3. Linking a person makes them a sponsor in the People directory (`/portal/people`) going forward, and their other roles are unaffected. **Implemented** by the derived role model described in [§5.9](people.md#59-people-directory) rather than by the sponsor-linking code: the `event_sponsors` row _is_ what makes them a sponsor, and unlinking their last sponsorship stops it. While the roles were stored flags each caller had to remember to set, linking an _existing_ person set nothing and `/portal/sponsors` was missing sponsors (issue #620).
4. Per-event sponsorship details — support type (cash, in-kind, both, other), in-kind description, contribution value, public visibility, and notes — are stored on the event-sponsor link, not on the person record, since the same sponsor can support different events differently.
5. A person may be linked to a given event only once; re-selecting an already-linked person edits the existing link rather than creating a duplicate.
6. An in-kind sponsorship is mirrored into `donations` + **one `inventory_items` row per item** (issue #1005) so the goods are tracked and valued like any other donation. A sponsor hands over several distinct things at once — a board, goggles, five tees, four lift tickets — and each has its own fate, so the Sponsors tab records a list: description, value and destination per row. The items _are_ the inventory rows under `event_sponsors.donation_id`; there is no sponsor-items table, which is what makes the rest of the app work on them unchanged. Each appears separately in the Giveaway tab's prize-source picker (`list_available_giveaway_sources` already lists every inventory item on the event's donations), so items can be combined across prizes and buckets however the draw is run.

   Each item's `intended_use` defaults to `giveaway`: sponsor contributions are usually vouchers, gift cards or lift tickets destined for an event giveaway, not gear for the community to take home, so by default they reach neither the public gear catalog, the public request flow, nor the rider distribution picker. An item the staffer sends to `gear_library` does reach all three — that is the point of the per-item destination, and it is how a sponsor's gear gets onto the public site. Items can still be reclassified afterwards from Inventory › Items.

   Removing an item is refused while a giveaway prize names it (`giveaway_prizes.source_inventory_item_id` is `on delete set null`, so an unguarded delete would empty the prize in place) or while it carries movement history beyond its intake. The tab disables that row's remove control rather than letting the staffer hit the error.

   `in_kind_description` is derived from the item descriptions rather than typed, so the two can never disagree, and `contribution_value` stays a manual figure that defaults to the items total. `'both'` mirrors its in-kind half on the same terms; its cash half remains unmirrored, since one `contribution_value` cannot be split into cash and goods without inventing a number.

**Where a public sponsorship shows** (issue #914): on its event's detail page, and on the tenant's `/support/sponsorship` page, through the `public_sponsor_wall` view -- the same join as `public_event_sponsors` with the event dropped and one row per person, so a logo no longer leaves the public site when its event ages out. **The wall has two arms and two opt-ins** (#1024). The first is a sponsorship marked `is_public` on a published public event, above. The second exists for a sponsor who supports the organization rather than an event -- an annual partner, a business funding a program -- who has no sponsorship to mark and could previously reach the public site only behind a fake event: a `person_role_tags` sponsor assertion carrying its own `is_public`, ticked on the person form. That arm is **organizations only**, on the same grounds as the logo and website it publishes: the wall shows a mark, and an individual with no logo would be published to a public page as their own name. Both arms stay derived rather than curated -- neither writes a second copy of a sponsor's name, logo or website, which always come from the one `people` row -- and a sponsor who is both event-credited and hand-published appears exactly once. The heading and intro above the logos are tenant-owned copy (`support.sponsor_wall_heading`, `support.sponsor_wall_intro`), and a tenant with no public sponsors renders no section at all.

## 6. Data model — Public and events

- `pages` or repository content: approved public content
- `events`: `group_chat_enabled` (default false) and `group_chat_label` (at most 40 characters, null reads "Group chat"): **implemented** (issue #1648). See "Group chat" above.
- `events.reminder_enabled` (default true for new events; existing events were left false), `events.reminder_days_before` (1 to 14, default 2) and `events.reminder_intro` (nullable, up to 1,000 characters): **implemented** (issue #1652). See "Event reminder" above.
- `events.carpools_enabled` (default false) and `events.carpool_seats_question_id` (nullable): **implemented** (issue #1649). The question pointer is deliberately **not a foreign key** -- a second relationship between `events` and `event_registration_questions` would make bare `event_registration_questions(...)` embeds of an event ambiguous (PGRST201) -- so a trigger requires a live `number` question of the same event, and archiving, retyping or deleting the question clears it. See "Carpools" above.
